## Decision: how a rebuild for a different key is kept from deleting a translator in use (CR-03 part b)

The planner read both options against the code. **Chosen: build into a key-named folder (`dmsh_xlate-<key[:12]>`).**

- **Rejected: hold the tools lock (`wait=True`) around the shaders stage's use of the dll.** `shaders()` calls `translator()`, which takes the same lock through `nuget.restored()`. A second `lock.take` on the same file in one process is a second open file description, and on POSIX its `flock` blocks against the first, so the port deadlocks. Avoiding that means restructuring `restored()` and `translator()`. It would also queue every other game's nx_extract and translator builds behind a shader translation that runs for minutes, which makes WR-02 worse.
- **Chosen, because it is the smallest change:** two assignments in `translator()` change, `out` and `kf`; the lock code is untouched. A folder is replaced only when its own key file is missing or different. That means a cut-off build of the same key, which no port can be using, because `translator()` returns only after the key file is written or matched. A rebuild for another key writes a different folder. On POSIX it also stops a port's later `shader_vk.py` runs from loading a different translator from the one recorded in its shaders key.
- **Cost (accepted, T-02-35):** each translator source change or .NET change leaves one folder of about 5 MB (the Mac prebuilt `dm/gfx/tools/dmsh_xlate_bin` is 4.8 MB). The first port after this update builds the translator once more, into the new folder. The old `<user dir>/tools/dmsh_xlate` and `dmsh_xlate.key` stay unused and can be deleted by hand; the SUMMARY's User Setup note should say so for the release notes. The `.partial` folder stays shared as `dmsh_xlate.partial`. It is only touched under the lock, so `porter/nuget.py`'s comment that names it stays true.

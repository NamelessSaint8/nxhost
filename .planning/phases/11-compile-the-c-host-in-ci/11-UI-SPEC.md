# Phase 11 — UI Design Contract

> Visual and interaction contract for the Port view's target choice (two checkboxes) and its
> per-target result rows. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> This is a PySide6 Qt Widgets desktop app (Fusion style), not a web app and not a shadcn
> project. Every value below is a Qt term: margins and spacing in px, font sizes relative to
> the application font, colours as palette roles or as the two hex pairs Phase 3 already
> declared in `gui/firstrun.py` (`COLOUR`, `colour()`). No design system is introduced, no
> image asset, no new font.
>
> **Scope of the UI half.** The phase has two halves. The CI half (D-09, QUAL-09) has no UI
> surface at all — nothing in this contract covers it. This contract covers exactly:
> 1. the **Targets** row in the existing Port view — `Android APK` and `Mac app`, both
>    allowed, a host-appropriate default, the Mac box disabled off macOS with the reason
>    (D-02, D-03);
> 2. the **per-target result rows** drawn after a run — built / failed / skipped with the
>    reason, each with its own **Reveal** (D-06, D-07, D-08);
> 3. the small consequences of those two: what the run passes to `porter`, the status line
>    and progress bar at the end, the stage list while two chains run, and the existing
>    Install row when Android is not ticked.

**Sources pre-populated (not re-asked):** `11-CONTEXT.md` D-01..D-09 (authoritative
behaviour); `ROADMAP.md` §Phase 11 criteria 1–4 and §Phase 9 (the `--platform` contract it
extends); `REQUIREMENTS.md` QUAL-06, QUAL-07, QUAL-09, QUAL-13; `gui/app.py` `PortTab`
(today's widgets, spacing and status line); `gui/firstrun.py` (the palette, `colour()`,
`mono()`, `Elided`, `cause()`/`failed()` this phase reuses); `gui/shell.py` (no Port view
yet); `tests/fixtures/bridge/port_ok.jsonl` and `port_build_error.jsonl` (the event shape a
per-target `result` must extend additively); `docs/ARCHITECTURE.md` (the GUI drives
`porter` and holds no pipeline logic).

**Where this lands.** `gui/app.py` `PortTab` — the window the bundle opens until Phase 6.
`gui/shell.py` has no Port view today (its own header says so; Phase 4 owns it), and Phase 4
explicitly inherits D-02 (the remembered per-game choice, deferred in `11-CONTEXT.md`).
Write the two new pieces (`TargetChoice`, `TargetRow`) as one cohesive pair beside
`PortTab` so Phase 4 lifts them into its Port view unchanged — one code path from view to
pipeline, never two.

| Token | Value | Usage |
|-------|-------|-------|

| sm | 8px | Between the two target checkboxes; between the parts of a result row (glyph, name, path, Reveal); between result rows |

| lg | 24px | unused this phase |
| xl | 32px | unused this phase |
| 2xl | 48px | unused this phase |
| 3xl | 64px | unused this phase |

Sizes:
- Result rows: no fixed height. The name line is one line; the path elides; the reason line
  word-wraps to as many lines as it needs.

- The Targets row: default checkbox height; the two boxes 8 px apart, no stretch between

Exceptions: the Port tab keeps Qt's default group margins (about 9–11 px depending on the
host) and the form's default row spacing, as Phase 3 declared for today's tabs. The three
values above are the only new ones.

## Typography

`P` is `QApplication.font().pointSizeF()` on the host. Sizes are relative so the view scales
with the user's system font. No pixel font sizes, no new family.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (target box labels, the note line, each result row's name+status, its reason) | P | Normal (400) | Qt default (`QFontMetrics.lineSpacing`, about 1.2). Never set a CSS line height |
| Mono (the package path in a result row) | 9 pt fixed (`firstrun.mono()`) | Normal (400) | Qt default |
| Primary button (the Port button, unchanged) | P + 2 | Bold (700) | Qt default |

Weights: exactly two, `QFont.Normal` and `QFont.Bold` (`setBold(True)`, which the Port button
already uses). This phase adds no bold text: the target box labels and the result rows are
Normal. The `·` separator and the status word are plain text, not a second size or weight.

Glyphs are the app's existing Unicode set (`✓` `✗` `–` `!` `▶`) in the same font as their
line — never an icon file.

## Color

Fusion follows the system light or dark scheme, so surfaces come from palette roles and are
never hard-coded. This phase adds **no** colour constant: the glyphs and the note line take
`firstrun.colour(self, key)` with the `ok` / `bad` / `note` pairs Phase 3 already measured.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `QPalette.Window` (Fusion light about `#efefef`) | The Port tab's background and the results block |
| Secondary (30%) | `QPalette.Base` / `QPalette.AlternateBase` | The stage tree, the log pane (existing) |
| Accent (10%) | `QPalette.Highlight` (system accent) | Only the elements listed below |
| Destructive | light `#c62828`, dark `#ef9a9a` (`COLOUR['bad']`) | A failed row's `✗` glyph and the status word `failed`; `[RED] ` log lines, as today. No destructive button in this phase |

Accent reserved for (unchanged from Phase 3, nothing added):
1. The `QProgressBar` chunk (Fusion draws it in Highlight already).
2. The selected row in the stage tree and in the device combo's popup.
3. Rich-text links (`Retry`, and any `Open log` link) via `QPalette.Link`.
4. A default button, when the Port button is the window's default. Nothing here forces it.

Status colours per row (glyph and status word only; the path and the reason text stay
`QPalette.WindowText`/`Text`):

| Row state | Glyph | Colour key | Word |
|-----------|-------|------------|------|
| built | `✓` | `ok` (`#2e7d32` light / `#81c784` dark) | `built` |
| failed | `✗` | `bad` (`#c62828` / `#ef9a9a`) | `failed` |
| skipped | `–` | `note` (`#9a5b00` / `#ffb74d`) | `skipped` |

The reason line under a row uses the same pair as its glyph. Colour is never the only
signal: every row has its glyph **and** its word.

The note under the Targets row is `COLOUR['note']` (`!` glyph in the same colour, then plain
text). Nothing on the Targets row is coloured when it is valid and reachable.

Do not edit `STATUS_COLOUR` in `gui/app.py` (it is the game status badge, a different axis)
and do not add a second palette table.

## Interaction Contract

### The Targets row (D-02, D-03, QUAL-07)

1. One new first row of the Options form: `f.addRow('Targets', row)`, where `row` is a
   `QWidget` holding `android = QCheckBox('Android APK')` and `mac = QCheckBox('Mac app')` in
   a `QHBoxLayout` (spacing 8, contents margins 0), then a stretch. The label column reads
   `Targets`.
2. Labels are exactly `Android APK` and `Mac app` — the noun the row's own status line and
   result rows reuse. No `&` mnemonic in either label (Phase 3's rule for this app).
3. Tooltips, set once at construction:
   - `Android APK`: `The APK and the data pack for your Android device`
   - `Mac app` (reachable): `A double-clickable Mac app, built on this Mac with Xcode`
   - `Mac app` (disabled): `A Mac app is built on a Mac: this host builds the Android APK`
4. **Default, by host fact** — one module constant in `gui/app.py`,
   `MAC_HOST = sys.platform == 'darwin'` (the GUI's only host check; it decides whether a
   box is *offered*, never whether a game can be ported):
   - macOS: `mac.setChecked(True)`, `android.setChecked(False)`, both enabled.
   - Windows / Linux: `android.setChecked(True)`, `mac.setChecked(False)`,
     `mac.setEnabled(False)`.
   - Read `11-CONTEXT.md` D-02 as one ticked box per host ("on macOS the Mac app is ticked,
     everywhere else Android is"). If the developer wants both ticked on macOS, that is one
     changed line in the default list; nothing else in this contract moves. Flagged as a
     `checkpoint:decision` for the planner.
5. **No zero-target state is reachable (D-02).** A change that would leave neither box ticked
   is reverted inside the slot, with signals blocked while it is reverted (no recursion):
   the clicked box re-ticks itself and the run never becomes invalid. Off macOS this is the
   only reachable refusal, because `mac` starts unticked and disabled — unticking `android`
   there is refused by the same rule, not by a separate one.
6. **The note line.** One `QLabel` under the row, plain text, word-wrapped, note colour,
   hidden when its text is empty. First match wins, and it is refreshed on every change and
   on every run start/finish:
   1. a refusal just happened → `Keep at least one target ticked.`
   2. off macOS → `A Mac app is built on a Mac. This host builds the Android APK.`
   3. `android` unticked (a Mac-only run) → `Install on the device and the device list apply to the Android APK.`
   4. otherwise hidden.
7. `mac`'s enabled state is only `MAC_HOST`; nothing else disables it. In particular the view
   never disables `android` for a game whose profile has no `android.tsv` (D-07): porter
   decides that, and it comes back as a `skipped` row with porter's reason.

### What a run passes to porter (QUAL-06, QUAL-07)

8. `start()` builds the platform argument from the two boxes through one helper, never from
   any other source:
   - both ticked → `--platform both`
   - only `android` → `--platform android`
   - only `mac` → `--platform mac-app`
   `--platform` is always passed explicitly (today a single-target run omits it and porter
   defaults to `android`); an unticked target is never named.
9. `--install` (and `--device`) are passed only while `android` is ticked. A Mac-only run
   passes neither.
10. The **Install on the device when done** row (its checkbox, the device combo, `Refresh`)
    is enabled exactly when `android` is ticked and no run is active. When it is not, the
    note line (rule 6.3) says why. This is the only existing option that gains a rule: the
    Development build and Experimental rows stay as they are, because porter owns what each
    target honours and a both-run still uses them for the Android chain.
11. While a run is active (`self.porter.running()`, from `run()` to `on_finished`), both
    target boxes are disabled, like the Port button; the note line stays as it is and
    `Cancel` stays enabled. On finish they are re-enabled with rule 4's reachability: `mac`
    only on macOS, and never leaving zero ticked.

### While two chains run (D-04, D-05)

12. The stage list stays one flat `QTreeWidget` with no new hierarchy. When the run has more
    than one target, the **Stage** column reads `<Target> · <stage name>` — e.g.
    `Android APK · rewrite`, then `Mac app · rewrite` — and the step line above the progress
    bar takes the same prefix: `Mac app · [3/7] host · NDK android-ndk-r27c`.
13. The prefix exists only for a multi-target run; a single-target run keeps today's
    unprefixed text so the golden streams and every existing screenshot still read the same.
14. `self.step.setWordWrap(True)` is turned on this phase: with a target prefix it can now
    exceed the window width at 980 px, and today's label has no wrap.

### After a run: the per-target rows (D-06, D-07, D-08)

15. The results block is hidden until a `result` event arrives, and cleared at the start of
    every run (`run()` clears it exactly as it clears the stage tree and the log). There is
    no empty-state heading, no placeholder row, no "no results yet" copy.
16. On `result`, the block draws **one row per target**, in the run's order (Android first,
    then the Mac app — D-04), from `result['targets']` (see the protocol surface below). A
    single-target `result` without a `targets` list draws exactly one row from the top-level
    fields (`platform` + `apk` / `app`), so the view has one shape and today's goldens stay
    valid.
17. A row is, in a `QVBoxLayout` (spacing 4):
    - line 1: `QLabel` glyph (fixed width, `firstrun.colour(self, key)`), `QLabel`
      `<Target> · <word>` (plain text), `firstrun.Elided(out)` with stretch 1 in
      `firstrun.mono()`, and the **Reveal** button;
    - line 2: a word-wrapped `QLabel` with the reason, in the row's colour, hidden when the
      row is built.
    A `failed` or `skipped` row with no `out` shows no path and a disabled `Reveal`.
18. Row words, exactly: `built`, `failed`, `skipped`. They are the run's own vocabulary
    (D-06) and are shown in lower case, after a `·`.
19. **Reveal** per row: `QDesktopServices.openUrl(QUrl.fromLocalFile(<the folder holding that
    target's package>))` — for the APK its folder, for the `.app` the folder that holds the
    bundle (today's `open_out` behaviour, one per row). Tooltip
    `Show <the Android APK | the Mac app> in your file manager`, and
    `setAccessibleName('Reveal the Android APK' / 'Reveal the Mac app')` so two buttons with
    the same label are distinguishable to a screen reader. Enabled only on a `built` row.
20. **Install on device** (the bar button, unchanged label and position) is enabled only when
    the `android` row is `built` and a device is chosen; it installs from that row's package
    plus the result's `data` folder, exactly today's `porter install` call. A Mac app is never
    installed by the GUI.

### The end of the run: status line and bar (D-06)

21. Exit 0 whenever nothing failed → `done in <took>` and the bar at 1000. That covers every
    target built, and a build with another target `skipped` (D-07's skip is not a failure): the
    skipped row carries its own reason, and the status line never invents a third string.
22. Exit non-zero with at least one target built (a partial success — the failing target did
    not stop the other) → `finished in <took>: the <names> failed`, the names joined with
    ` and `, and **the bar still at 1000**: something was produced, so an empty bar would say
    nothing happened. This is the one case today's `on_finished` would mis-report, because
    porter exits non-zero when any target failed.
23. Nothing built → today's `failed after <took>: <cause>` and the bar at 0, unchanged.
24. Cancelled (code 130 / `self.cancelled`) → `cancelled`, bar at 0, the `[RED] cancelled`
    log line, unchanged. No confirmation dialog for Cancel, unchanged.
25. A run that dies before a `result` event (the `error` event, the fixture
    `port_build_error.jsonl`) shows no rows: today's status line and `failed()`/`cause()`
    text carry it, and `Open log` stays enabled.

### What this view never does

26. It never reads the game folder, the profile, `android.tsv` or `dmsh_chain.lock`. Every
    "why" on screen is porter's `reason` string, escaped and shown as plain text, never
    reworded in the GUI (porter writes player-friendly English; see Copywriting).
27. It never computes whether a target can be built. `MAC_HOST` decides whether the Mac box
    is *offered*; porter decides whether a Mac build is possible and reports `skipped`.
28. It never starts two porter runs, never runs the two chains concurrently (deferred), and
    never falls back to a second code path when a target is skipped.

### Protocol surface this contract needs (additive only, D-08)

The view can honour the rows above only if porter sends these. Field names are the plan's to
pin; the obligation is what matters:

- `result` gains `targets: [{platform: 'android'|'mac-app', status: 'ok'|'failed'|'skipped',
  out: <absolute package path or ''>, reason: <string or ''>}]`, present only for a run with
  more than one target. Single-target runs keep today's shape (`apk`, `data`, `app`,
  `platform`).
- `stage`, `step` and `progress` gain `platform`, so the Stage column and the step line can
  carry the target prefix without the GUI guessing which chain is running.
- The run log names both targets (D-08) — the GUI only opens it.

## Copywriting Contract

Plain English, sentence case, no exclamation marks. The GUI's own copy never says "porter"
(Phase 3's rule: players see "nx2android"); porter's own `reason` and error strings are shown
as they arrive, escaped, never reworded.

| Element | Copy |
|---------|------|
| Primary CTA | `Port` (unchanged — the button, its bold P+2 font, its 36 px height and its enabled rule all stay as they are; the target row explains itself) |
| Targets row label | `Targets` |
| Target box, Android | `Android APK` |
| Target box, Mac app | `Mac app` |
| Targets tooltip (Android) | `The APK and the data pack for your Android device` |
| Targets tooltip (Mac app, reachable) | `A double-clickable Mac app, built on this Mac with Xcode` |
| Targets tooltip (Mac app, disabled) | `A Mac app is built on a Mac: this host builds the Android APK` |
| Note: a target was refused | `Keep at least one target ticked.` |
| Note: off macOS | `A Mac app is built on a Mac. This host builds the Android APK.` |
| Note: Android unticked | `Install on the device and the device list apply to the Android APK.` |
| Result row words | `built` · `failed` · `skipped` (after `<Target> · `, lower case) |
| Result row action | `Reveal` |
| Reveal tooltip | `Show the Android APK in your file manager` / `Show the Mac app in your file manager` |
| Empty state heading | none — the results block is hidden until a result arrives (Interaction 15) |
| Empty state body | none — there is nothing to say before a run; the Game card and the stage list already say what is happening |
| Error state (a target failed) | `<Target> · failed` plus porter's own `reason` on the second line, word-wrapped. The status line reads `finished in <took>: the Mac app failed` when the other target built |
| Error state (no result at all) | today's text, unchanged: `<cause>` + Retry, or `failed after <took>: <cause>` with `Open log` |
| Status line, partial success | `finished in <took>: the Android APK failed` (names joined with ` and ` when both failed and something still built) |
| Destructive confirmation | none in this phase. Cancel keeps today's behaviour (no dialog, `stopping…`, then `cancelled`) |

Wording rules for the strings above:
- Labels and buttons carry no trailing full stop; sentences do.
- `…` is the single-character ellipsis (Qt text, not `...`), as elsewhere in the app.
- The three note lines are one label: only one is ever visible at a time (rule 6), so they
  never stack.
- A `skipped` row's reason is **porter's** sentence, verbatim — the expected shape is
  `no android.tsv for this game: it has no Android profile`, and the plan must confirm porter
  writes it in player words. The GUI must not substitute its own.
- Never in any copy: a target name the user did not pick, the word "checkbox", a tool name
  (Xcode, Metal, NDK) other than where porter's own reason names it.
